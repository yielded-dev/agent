Tail-latency investigation, 2026-10-09 UTC. [PR #831](https://github.com/yielded-dev/agent/pull/831) removes 13 redundant maintenance-state writes per warm turn, **but the same-Object A/B does not demonstrate a reliable latency improvement**. CI and `vp run ready` pass; nothing is merged. Yielded has not reached parity with pi. The safe deletions examined here did not separate latency from noise, and the final diagnostic did not identify another supported change within alarm, maintenance, allocation or platform-gate scheduling.

The framework baseline is `07f0272e7ba49a494064b6b74c6318b55514ae19`, including #827. The harness is PR #828 at `78cb4eb7589984c1cd194e0cb01a5a0055a6d3f3`; both remote heads were refreshed before the final experiments. The separate bench checkout's sole lagging framework file, `storage-cloudflare/src/internal/owned-state.ts`, was aligned to the baseline for working-build runs. Instrumentation and bench changes are confined to the evidence branch, never the product PR.

All timing comes from deployed Cloudflare. The driver measures submission through observed settlement. A turn makes nine model calls and eight sequential lookup tool calls. The seeded model-visible fingerprints remain `b017b487524e44a4` at 50 turns and `dcea9f30b0917245` at 250.

The PR is retained for its separate, measured reduction in redundant work. [All pi controls and quantiles](maintenance-table.md), [compact warm samples](maintenance-latencies.json), and [stages, CPU, readiness, outcomes and ratios](maintenance-summary.json) preserve the comparison. The bootstrap uses 2,000 paired Object resamples within each framework, independently resampled between Yielded and pi; it does not treat repeated turns as independent Objects.

Attribution does not support one universal maintenance explanation. Every initial warm Yielded turn had 34 storage transactions; pi had 77 in nearly every turn. Yielded's SQL count was roughly 220–223 at 50 seeded turns and 257–261 at 250. Among all 55 initial Yielded spikes, 17 had admission time more than 250 ms above their Object median and 32 had excess after admission; two satisfy both. Eleven have at least one attributed invocation with more than 250 ms of CPU excess, and two are missing CPU attribution. Two have provider-reported elapsed excess above 250 ms. These [overlapping signals](distribution-spike-signals.json) are not exclusive causal categories.

All 960 initial warm Yielded turns entered with no previous alarm handler active. The harness reads metrics outside the timer between repeats, so this describes its cadence, not every possible client cadence. Range rotation occurs once per Object, at repeat 12 for 50 seeded turns and repeat 2 for 250, matching the 1,024-record bound. It adds three scalar SQL statements and does not copy the archive. Only three of the 40 rotation turns crossed the spike threshold; none of the largest outliers coincided with rotation. Archive export, lifecycle caching and application maintenance lanes are disabled in this workload.

The three observed alarm writes have different purposes: ingress at now+50 ms, a charged-wave fallback at now+1000 ms, then advancement to now+50 ms after actual progress. Removing one changes recovery deadlines. There are 31 transactions by `await:return` and 34 by `alarm:end`; the final gated reread protects a producer racing with retirement. A [scan of 960 settlement timelines](settlement-gap.json) found just two positive Object-clock terminalization-to-await-return gaps, 377 and 451 ms. Both await RPCs entered after terminalization and alarm return, then returned on the same tick. This does not support a missed notification followed by the 500 ms fallback.

FinalizationRegistry callbacks appeared during essentially every turn in both frameworks. They count collected sentinels, not GC cycles or pause duration. Their [nondeterministic behavior](https://blog.cloudflare.com/we-shipped-finalizationregistry-in-workers-why-you-should-never-use-it/) and lack of separation between typical and slow turns do not justify an allocation rewrite. Target-side transcript verification also clones, parses and hashes requests inside the timer; invocation CPU includes this bench work. That is a measurement-method lead for the bench owner, not an attributed product gain.

The initial run also captured a different provider-side anomaly: at 250/instant, Object 0's turn grew from 956 to 2936 ms while summed provider-reported elapsed grew from 17 to 801 ms. At that same repeat, all ten Objects sent the same 157,772-byte first request, but the other providers reported 0–49 ms. The [equal-workload slice](provider-slice.json), [initial pairs](distribution-attribution.json), and [route evidence](distribution-routes.json) keep that lead for the bench owner. Request size alone does not explain that isolated event.

Object `Date.now()` is an [I/O clock](https://developers.cloudflare.com/workers/runtime-apis/performance/); it did not advance between submit entry and framework return in this diagnostic. The sync span can include a stale starting timestamp, alarm precommit scheduling and resumption; [sync waits for pending storage](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/#sync), so its span is not isolated disk time. Driver, provider and Object clocks are separate domains. [Invocation wall time](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/#wall-time-per-execution) can include context lifetime after a response. Overlapping alarm/await spans are never summed. The narrow query recovered 13 of 14 caller RPC spans, all 14 driver records and 120 of 126 provider invocation records; missing observations remain missing.

A bench correctness issue affected earlier A/B labels. After candidate → baseline deployment, one newly reconstructed Object kept the candidate's five-write signature while the Worker reported baseline. A [version audit](maintenance-version-audit.json) independently mapped Worker and Object invocation versions to their deployed BUILD bindings. This matches Cloudflare's warning that [Worker and Object code updates can propagate separately](https://developers.cloudflare.com/durable-objects/platform/known-issues/#code-updates). The built source archives contained the intended framework revisions.

The local harness now waits for the Object's own BUILD during cold readiness, checks it before input admission, and checks completed metrics and provider receipts. The final successful reset is followed directly by the timed cold input. A [32-input pilot](build-guard-pilot.json) verified this guard before the accepted A/B. Only setup resets are retried; uncertain inputs are never replayed. The [complete instrumentation patches and commands](reproduce.md) are available for the bench owner. The guard belongs upstream in #828; no sibling product code was edited.
