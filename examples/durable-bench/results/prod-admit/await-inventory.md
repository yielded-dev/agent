This records source dependencies and the measurement owner's reported transaction counts; it does not report measured phase durations. Product source links are pinned to that commit. Harness links are local evidence references, read without modification, and can move as the owner develops the diagnostic.

The deployed trace supplied by the measurement owner shows **four native asynchronous storage transaction calls on each seeded fresh admission: prearm → admit → markReady → wake**, plus **five additional constructor transactions on cold acquisition**. Here, “fresh admission” means a new idempotency key on an already materialized, seeded thread. It does not mean a new thread or a new Object incarnation.

**Four sequential transaction promise completions are established; four durability waits or four replication roundtrips are not.** The supplied Workerd source finding is that `actor-sqlite.c++`, `ExplicitTxn::commit`, releases the local SQLite savepoint and returns no backpressure. Replication and alarm scheduling lock the **OUTPUT gate**, rather than being awaited by that transaction's JavaScript promise. The Effect driver awaits the native transaction promise; that alone cannot identify when the output gate opens or how much time durability adds to the RPC response.

Every recorded `Date.now()` within each reported invocation was frozen, and warm invocations could retain a timestamp from a prior invocation. These timestamps establish neither zero-duration phases nor cross-invocation elapsed time. The separate entry-echo plus final-`storage.sync()` diagnostic is in [network/yielded.ts](network/yielded.ts); its results are retained in [diagnostic-admission.json](diagnostic-admission.json). This inventory records ordered source dependencies rather than assigning wall time to frozen trace points.

The warm seeded/default driver-to-receipt order is below. Defaults mean ordinary root input, local ownership, no custom publication/projection/lifecycle hooks, no active maintenance-pass wake deferral, no admission race, and successful execution.

The driver's timer read follows definition hashing in source order, but its I/O clock can still equal the preceding probe-completion timestamp. Consequently the reported primary interval can include hashing and client setup between that probe and the nominal timer read. It is not an exact sub-millisecond stopwatch around native RPC alone.

The SQL driver boundary is explicit in the installed `@effect/sql-sqlite-do` source: [SqliteClient.ts:126–182][sql-transaction] calls `storage.transaction`, resumes the Effect body, resolves its callback, and awaits the native transaction promise in the exit path. Its [statement implementation:207–230][sql-statement] calls `storage.sql.exec` and consumes cursor rows synchronously inside `Effect.try`. Transaction scheduling disables automatic Effect scheduler yields there; semaphore contention can still suspend before acquisition. [BrowserCrypto.ts:69–91][browser-crypto] uses `Effect.tryPromise` for `crypto.subtle.digest`. `yield*`, service lookup, `Effect.suspend`, schema validation, timestamps, and UUID creation are not intrinsically promise boundaries.

The host source transaction chain is [sourceOwner.transaction:638–660][source-owner] → [ThreadMutationGate.withTransaction:1003–1004][gate-transaction] → [DueQueue.withTransaction:192–248][due-transaction] → the SQL driver. `makeStorageOperation` is a promise wrapper/reservation helper, despite some callers naming it `runTransaction`; [Alarm.ts:91–123][storage-operation] does not itself create a native transaction. [recordProgress:965–999][progress] checks the ambient source transaction, updates buffered due metadata, awaits maintenance KV `get`/`put` and alarm inspection/update, then notifies local waiters. Due-queue SQL flush and source data share the same atomic transaction. Do not count those helper promises as extra transaction calls or confirmed independent durability waits.

Within the admission transaction, storage and decode order is:

1. Before transaction entry, [ledger:1122–1190][ledger-admit] validates `AdmissionRequest`, serializes input/definition/optional metadata, checks stored-value limits, and mints submission/receipt UUIDs, including on replay. These are CPU/schema operations with the installed UUID implementation.
2. [byKey:532–554][lane] obtains `laneWork`: `SELECT` up to 129 control rows on a miss, schema-decodes them, and retains only complete lanes of at most 128 rows. A small lane filters this view and hydrates matching full rows. Overflow uses an indexed tuple lookup. `admit` validates those already-decoded full rows again at line 1199.
3. A retained row compares input digest, parent linkage, group, fence and worker/message metadata, then returns its original receipt/submission/queue identity. This branch occurs **before mutable worker-stop, fence-policy, or group-occupancy checks**. The core replay branch does not need full retained input JSON decoding; the host's earlier `lookup` can decode a full snapshot to establish existence.
4. Fresh admission checks transfer-page bounds; reads worker-stop state; obtains `laneWork` a second time; reads/decodes the first accepted input's worker-origin metadata; invokes the admission fence; optionally queries occupied admission group; obtains/decodes the next queue sequence. Small lanes hydrate the first full submission merely to read `worker_admission_json`; large lanes select that column and query `MAX(queue_sequence)` separately. [Fresh branch:1282–1370][fresh-admit].
5. Insert `admitted` with `RETURNING *`, decode/update caches, preserve the [transfer admission-count trigger:96][transfer-trigger], and seed proven-empty submission-owned views. Queue sequence one checks thread existence and initializes the work catalogue if absent. Source progress runs inside the transaction; decode `AdmissionResult` and await the native transaction promise. [Writes:1374–1453][admit-writes].

The host's preceding [nonterminal scan:3792–3837][nonterminal] reads control metadata, not canonical history or all input bodies. It uses a complete active-set cache up to 128 rows, otherwise a paginated SQL scan. The physical owner's [row views and rollback invalidation][owned-state] are shared across ledger/thread operations and updated by `RETURNING`. Repeated `getThread`, `requireSubmission`, and `laneWork` calls therefore do not necessarily repeat SQL. For a lane above 128 retained submissions, however, the host lookup and both admission lane probes can each execute `LIMIT 129`; only the two probes within the admission transaction have an immediately reusable observation without crossing a transaction boundary.

**Lifecycle publication is optional and disabled on this default path.** [sharedLayer:630–634][lifecycle-option] installs it only when explicitly configured. When enabled, `markReady` retains `SubmissionReady`; [SqlLifecyclePublication.retain:478–482][lifecycle-retain] first flushes the owner's pending canonical suffix. [flushCanonical:1339–1398][lifecycle-flush] defaults to `maxRecords = Infinity`, reads pages of at most 128, JSON-decodes every record, validates sequence/identity, retains relevant facts, and advances the cursor. Retention can query fact identities/maximum ordinal, hash payload fingerprints, and insert intent in the source transaction. This is a possible admission-time history dependency and extra crypto work, not a default seeded-admission history scan or an external sink call. Enabling lifecycle also adds [idempotent table/index DDL:325–343][lifecycle-ddl] and [once-per-owner cursor initialization:1302–1335][lifecycle-init] during acquisition; the message-store factory can acquire publication support separately too.

Worker/message options also leave the ordinary-root map: [peer admission validation:608][peer-validation] reads source/prepared-message evidence; [worker admission validation:1565][worker-validation] can validate continuations, authorize and reserve capacity/budget before target admission; [completion validation:3769][completion-validation] verifies canonical completion/origin/input evidence and live authority. The [worker admission port:49][worker-admit] additionally ensures `WorkerOriginRecorded`. No fixed transaction count is claimed for these branches.

The actionable read reductions carried forward from the source scout are limited:

- Reuse the lane observation **within the admission transaction** between `byKey` and first-origin/queue allocation. Above 128 retained rows, this removes one repeated SQL query and row decoding; at or below 128, it removes sorting/evaluation only. The host's earlier observation crosses prearm/hash scheduling and cannot replace the transactional uniqueness/fence decision.
- Remove repeated internal decoding of rows already validated by the owner cache (`admit` line 1199, lookup line 1568, materialize line 534), while retaining SQL/`RETURNING` boundary validation and cardinality checks. This is CPU reduction, not elimination of a promise or durability wait.
- Narrow cold first-origin hydration instead of reading an entire old input row for one metadata field. Retain the transactional ordinary/worker-origin comparison; a warm full-row cache already avoids the query.
- Share validated cold layout acquisition within one physical-owner/configuration graph. Preserve independent reopen checks, incompatible-version refusal, failure invalidation, and accounting. This is an acquisition refactor candidate, not permission to remove initialization checks globally.

Retain canonical `ThreadCreated`, live append fence/tail checks, immutable receipt comparisons, queue ordering, transfer triggers and counters, archive byte accounting, pre-materialization work discovery, and source-atomic maintenance enrollment. Keep lifecycle ordering if that option is enabled. No source change is proposed for turn processing, and no awaited transaction is described here as a measured replication roundtrip.
