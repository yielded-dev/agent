Part I

How a Thread is built

Ownership

One object used to do four jobs

The old Thread was the conversation, the execution log, the recovery state and the resource counters at once. Every bound came from those being the same object. Now each job has one owner.

Before · one Thread

Now · one owner per job

Conversation historywhat the model saw, stored as log records
Context windowWhat the model sees. Bounded by tokens and owned by compaction, which never touches the log.
Execution logthe same records, in one digest chain
Thread logOne continuous append-only log with no record cap. The Thread owns identity, admission, fencing and idempotency.
Recovery staterebuilt by walking the log, from a checkpoint if its format still matched
ContinuationOne per Run, versioned, written with each transition. It says where execution can safely resume and references the exact facts it needs.
Counterspeer messages, workers, deliveries: counted for the Thread’s lifetime, never released by finished subagents
Counters by purposeConcurrency is counted Thread-wide. Retention is counted over a window.

Storage partitionsSealed ranges of the log, archivable and read by reference. The interpreter never sees them.

Recovery

Resuming a Run after a crash

The cost moves from the age of the conversation to the size of the open work. Both diagrams show the same Thread of 81,250 records.

Recovery of one Run is bounded by its open work. A new Run is different: before its first model call it assembles the model’s view of the conversation from the log. Without compaction, that view is the whole conversation. Part II measures that step.

Reads

One log, three readers

The log stays one sequence. Storage can seal old ranges into partitions, and nothing above the storage adapter notices. Each reader loads only what bounds it.

Formats

Changing a format

One version number used to cover the table layout and the meaning of every record. Now three kinds of data follow three rules.

Before · one gate

user_version N → N+1

One number covers the table layout and every record’s meaning. A change takes one of two paths.

  • Adapter-owned SQL rewrites of payloads, ledger rows and checkpoints
  • Refuse the store and start fresh

Part II

What a turn costs, measured

One workload, one machine, one platform. The examples/durable-bench bake-off runs the same scripted conversation in a SQLite Durable Object for Yielded Agent and for pi-durable 1.0.4. Because the platform is held constant, the differences belong to the libraries.

Cost as a Thread ages

Every line grows. Ours grew fastest.

Compaction is off for every target, so each model call sees the whole conversation and no line can be flat. main also stored a list of every prior record with each Run, so its log grew quadratically and Runs were refused past about 1,230 turns. The spike stores a fixed-size boundary instead.

Anatomy of a warm turn

Both rebuild the conversation. pi’s rebuild is far cheaper.

Each turn makes nine model calls and eight tool calls. Before the first model call, our runtime reads the conversation from the log, decodes and projects it, and commits the Run’s start. pi starts almost immediately, then re-reads its conversation from SQLite on every model request: at least nine full rebuilds per turn. It still spends less, so the gap is our cost per record, not how often we rebuild. Once the model calls begin, our steps are cheaper than pi’s.

What grows inside our steps. The engine estimates the prompt’s tokens on every model call even when no contextTokenLimit is set: about 11 ms per turn at 1,000 turns and 44 ms at 3,500. The rest of a step (encode, hash and append the batch, write the continuation) is about 5–6 ms and does not grow.

What grows inside pi’s steps. Each model request scans the conversation’s entries from SQLite between its latest head marker and the tail, parses them and derives the context. Its benchmark harness then converts the transcript again; the harness alone is 24–30% of pi’s turn. Outside the harness pi spends about 98 ms per turn at 1,000 turns on at least nine rebuilds of 3,335 entries: under 3.3 µs per entry. Our one rebuild reads about 6,300 records in 280 ms: about 44 µs per record.

“Warm isolate” is about memory, not Cloudflare. In the bench, warm means later turns in the same Durable Object instance; cold means a fresh process, open and first turn. Node has the same split: a resident host process versus a restart.

Today the runtime reuses nothing between Runs on either platform, so our warm and cold turns differ only by JIT and codec warm-up (292 vs 389 ms at 1,000 turns). pi reuses no context either: its Durable Object keeps a conversation handle, not the context. The platform decides how often a cache would hit: Cloudflare evicts idle objects, so a turn after a pause often starts cold, while a Node host keeps memory until it restarts.

Saved context

Why main’s log grew quadratically

Each Run writes a RunContextRecorded with its start, so recovery can rebuild the exact prompt the Run began with. On main that record named every earlier history record by id, sequence and digest. Every new Run copied the list and added to it.

Tradeoffs

Verify history at the edges, not on every Run

Main re-proves the whole history whenever a Run starts: it resolves every earlier record, checks its digest, re-checks old tool declarations and projects the prompt again. pi trusts its stored entries and reads them. The cheaper design checks history when it is written, sealed, imported or used for cold recovery. That shift is what the remaining speed costs.

Method

How this was measured

  • Workload. The shared durable-bench conversation: history repeats a one-tool, one-tool, zero-tool cycle; each measured turn makes eight lookup calls. Tool results are 256 bytes, every 97th is 8 KiB. The model is scripted; nothing calls a provider.
  • Samples. Three samples per size, ten turns each. Warm is the median of turns two to ten; cold is open plus the first turn. The harness waits for CPU below 8% before each sample; the comparison runs averaged about 6%.
  • Transcripts match. The model-visible transcript fingerprints are identical for pi, main and the spike at every size.
  • Profiles. V8 sampling through the workerd inspector at 100 µs. Phases are split at the benchmark’s entry and scripted-model frames; layers by the bundled module of each sample’s innermost frame.
  • Revisions. main at 8ec0b4dc; the spike on branch dan/spike-saved-context-range; pi-durable 1.0.4 with compaction disabled.
  • Machine. Apple Silicon Mac, local Miniflare (workerd), compatibility date 2026-08-18, Bun 1.4.2. Local timings are not Cloudflare CPU billing.
  • Not measured here. Node. The tooling/runtime-benchmark suite (vp run perf:compare) covers Node and file-backed SQLite and is the release gate.
  • Fairness. Our scripted model receives the in-memory Prompt; a real provider would add request encoding to our steps too. pi’s harness converts the transcript on every call, which inflates pi’s steps.

Invariants

Rules that do not change

Every optimization above has to keep these.

  • The log is append-only.
  • Expected failures stay typed.
  • Every resource lives in a Scope.
  • No code claims exactly-once execution.
  • An unresolved ordinary tool call is never replayed automatically.
  • A continuation must be recomputable from the facts it references.Disagreement is corruption and fails closed.
